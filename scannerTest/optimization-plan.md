# 扫码优化方案回看

## 当前状态

- 之前的分辨率改动已经撤回，代码回到 baseline。
- 建议先用 `README.md` 里的 A/B 试验记录 baseline，再逐项应用优化。
- **不要一次把所有优化全加上**，否则无法判断是哪一项起了作用。

## 优化优先级

### P0：先解决输入质量

| 优化 | 做什么 | 预期效果 | 风险 |
|---|---|---|---|
| ImageAnalysis 分辨率 | 用 `ResolutionSelector` 指定 1280×720，替代默认约 640×480 | 远距离二维码像素更多，识别率提升 | 发热、耗电、单帧处理变慢 |
| analyzer 后台线程 | 不再用主线程 executor，改单线程 executor | 减少掉帧和主线程卡顿，更容易抓到清晰帧 | 需要正确关闭 executor |
| 相机生命周期清理 | 离开扫码页时 `unbindAll`，先停分析再关 scanner | 避免相机常驻、ImageProxy 泄漏、重进卡死 | 需要处理生命周期顺序 |

### P1：解决对焦和远距离

| 优化 | 做什么 | 预期效果 | 风险 |
|---|---|---|---|
| 点击对焦 | 点击画面位置触发 `FocusMeteringAction`，保留连续 AF | 斜角度、反光、背景干扰时更容易对焦到二维码 | 点击坐标要换算到相机坐标 |
| 手电筒 | 增加 torch 开关 | 低光环境提升对比度 | 近距离可能过曝 |
| 自动变焦 / ROI | 检测到二维码区域后放大，或对中心区域裁剪后再解码 | 远距离二维码在分析帧里更大 | 逻辑复杂，可能过度放大 |
| 预览/分析画面对齐 | 用 `AspectRatioStrategy` 或 `ViewPort` 统一比例 | 避免预览里看得到、分析帧里被裁掉 | 需要调 CameraX UseCase 组合 |

### P2：还不够再考虑

| 优化 | 做什么 | 预期效果 | 风险 |
|---|---|---|---|
| 多帧尝试 | 不在第一次失败后放弃，连续多帧尝试并保留结果 | 难扫的码更容易遇到清晰帧 | 耗电、延迟 |
| 换解码器 | ZXing-C++ 或 OpenCV `wechat_qrcode` | 极端角度/低分辨率下可能优于 ML Kit | APK 变大、集成成本高 |
| 调试日志 | 记录分辨率、二维码像素宽、解码耗时、成功/失败 | 让试验有数据可依 | 只放在 debug 构建 |

## 推荐执行顺序

```text
0. 先测 baseline（A）
1. 只改 ImageAnalysis 分辨率 → 测 A/B
2. 分辨率有效，再加后台 executor → 测 A/B
3. 再解决生命周期清理 → 测稳定性
4. 加点击对焦 → 测斜角度/低光
5. 加自动变焦/ROI → 测远距离
6. 仍然不够，再考虑多帧或换解码器
```

每加一项，只回答一个问题：

- 这项优化有没有让困难条件变好？
- 有没有让简单条件变差？
- 有没有引入崩溃、卡死、发热或耗电问题？

## 每项优化怎么验证

| 优化 | 重点看什么条件 | 主要指标 |
|---|---|---|
| 分辨率 | 远距离 3m | 成功率 |
| 后台 executor | 所有条件 | 掉帧、耗时、卡顿 |
| 生命周期清理 | 反复进出扫码页 | 崩溃、相机卡死 |
| 点击对焦 | 斜角度 45°、低光 | 成功率 |
| 自动变焦/ROI | 远距离 3m | 成功率、耗时 |
| 多帧/换解码器 | 远距离 + 斜角度 | 成功率、耗时、APK 大小 |

## 验收底线

- 困难条件（远距离/斜角度）成功率明显提升。
- 简单条件（1m、正对）成功率不下降。
- 简单条件耗时不能明显变差。
- 不增加崩溃、卡死、相机无法释放等问题。
- 如果某一项没有效果，就回退，不要因为“理论上应该有用”而保留。

## 一句话总结

**先把“输入质量”做好：分辨率、后台线程、生命周期；再做“对准”：对焦、变焦/ROI；最后才考虑“解码器”和“多帧融合”。每做一项都用 `scannerTest` 的 A/B 试验验证，不要一次性全上。**
